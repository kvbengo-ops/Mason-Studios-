# Local database with Docker

The [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started)
runs Postgres, Auth, Storage, Realtime, Studio, and a local email inbox in Docker.
The web app and Go worker run on your host and share this local database. The CLI
version is pinned in the root `package.json` and `bun.lock`.

## First start

Start Docker Desktop using Linux containers, then run from the repo root:

```sh
make install
make db-start
make db-env
make dev
```

The first start downloads container images and applies `supabase/migrations/` in
order. It starts with an empty local database plus the prompt templates and other
configuration already seeded by migrations. Production users, projects, and files
are not copied. Analytics and Edge Functions are disabled because the app does not
use them; Storage image transformations remain enabled.

`db-env` reads credentials from the running local stack and configures
`web/.env.local` and `worker/.env.local`. Existing files are backed up beside them
as `.env.local.before-local-<timestamp>.bak` before any change. Both the settings
and backups are gitignored. Unrelated settings are preserved; vendor keys are
blanked, both services use `MODE=development`, and their audio/assembly flags agree.
The worker's older `.env` file is left intact and is overridden by `.env.local`.
Restart any running app/worker after this step. Exported shell variables take
precedence over env files, so remove old exported connection settings first.

On Windows without Make, these are the equivalent commands:

```powershell
# Repo root
bun install
bun run db:start
bun run db:env

# Terminal 1
cd web
bun install
bun run dev

# Terminal 2, starting from the repo root
cd worker
go mod download
go run ./cmd/worker
```

Use Bun for the web app (the repository pins Bun 1.4.0), Go 1.25 for the worker,
and ffmpeg/ffprobe on your PATH if you want to exercise mocked video ingestion.
The root `docker-compose.yml` builds the application containers for hosted Supabase;
it is separate from this workflow. Host loopback URLs generated by `db-env` are
for host-run services and cannot be used inside those application containers.

## Connections

| Service         | Local address                                                             |
| --------------- | ------------------------------------------------------------------------- |
| App             | http://localhost:9000                                                     |
| Supabase API    | http://127.0.0.1:54321                                                    |
| Postgres        | `postgresql://postgres:postgres@127.0.0.1:54322/postgres?sslmode=disable` |
| Supabase Studio | http://127.0.0.1:54323                                                    |
| Email inbox     | http://127.0.0.1:54324                                                    |
| Worker health   | http://127.0.0.1:8080/health                                              |

Database name, username, and password are all `postgres`; SSL is disabled locally.
`make db-status` / `bun run db:status` prints the local API keys. These development
services and credentials are intended for your machine; do not expose them publicly.

## First login

Sign up through the local app. Email confirmation is disabled locally, but the
application's account approval still applies. To bootstrap your first local admin,
open **local** Studio's Table Editor, select `public.profiles`, find your new
account, and set `role` to `admin` and `status` to `active`. That local admin can
then approve other local accounts from `/users`.

## Everyday commands

| Make                  | PowerShell / Bun equivalent | Effect                                              |
| --------------------- | --------------------------- | --------------------------------------------------- |
| `make db-start`       | `bun run db:start`          | Start the stack; reuse existing data                |
| `make db-stop`        | `bun run db:stop`           | Stop the stack; preserve local data                 |
| `make db-status`      | `bun run db:status`         | Show local URLs and keys                            |
| `make db-env`         | `bun run db:env`            | Back up and configure both env files                |
| `make db-push`        | `bun run db:push`           | Apply pending migrations locally                    |
| `make db-reset`       | `bun run db:reset`          | **Erase local database rows** and replay migrations |
| `make db-push-remote` | `bun run db:push:remote`    | Apply migrations to the linked hosted project       |

Normal development uses `db-push`, which explicitly passes `--local`, even if the
checkout is linked to production. Remote migrations are a separate deployment
operation. `db-reset` removes local users/projects/history and has no automatic
undo; export anything you need first. Avoid `supabase stop --no-backup`, which
also discards local Docker data volumes.

`make db-test` resets the local database before running the worker's database
tests; it is destructive to local development data. Run ordinary application
checks with `make check`.

To return to previous connection settings, restore both services' saved env
files and restart both processes. If the worker had no `.env.local` before setup,
remove that newly generated file to let its original `.env` take effect again.
